# GoMessage Todos · V3

## 版本定位

V3 不只是一次常规修补。

它真正要做的，是让 GoMessage 从一个“把消息发出去的工具”，逐步形成更完整的产品形态：

- 消息背后有事件
- 事件背后有上下文
- 上下文背后有状态
- 状态背后有协作

一句话概括：

**V3 是 GoMessage 从消息转发器走向事件中枢的版本。**

## 为什么要做这一版

V2 时代的 GoMessage，已经能够完成消息接入、渲染与转发。

但它仍然更像消息流经的一环，而不是事件被稳定承接下来的地方。

这会带来一种持续存在的空缺感：

- 群里来了一条消息
- 人看到了
- 但看完之后，消息背后没有更深一层的承接
- 没有一个稳定的地方去回看、去追溯、去继续处理

所以 V3 真正要解决的，不是“再多支持几个功能点”，而是：

**让消息背后开始具备可承接、可追溯的事件层。**

这不是为了把产品做复杂，而是为了让 GoMessage 从“通知到达”进一步走向“事件落地”。

## 这一版最重要的感觉

如果 V3 做对了，用户的感受不应该只是：

> “它能把消息发到群里。”

而应该开始变成：

> “群里那条消息背后，有一个可以打开、查看、处理、追溯的事件世界。”

这就是 V3 最关键的变化。

## 用户画面

如果从一个过去的 GoMessage 用户视角来看，V3 应该出现下面这种更具体的画面：

### 画面一：消息不再只是消息

以前群里来一条告警，大家看到后往往只能：

- 复制
- 转发
- 手动再去找上下文
- 手动确认是谁处理

而 V3 之后，这条消息应该更像一个“有完整上下文的事件”：

- 看得到它的身份
- 打得开它的详情
- 找得到它的原始事实
- 追得回它的处理轨迹

### 画面二：专业用户不再被迫接受“替你理解”

过去很多系统一旦想“更友好”，就会直接把原始信息折叠掉，强行替用户做二次表达。

V3 不该这样。

V3 更理想的体验是：

- 你可以直接看原始 JSON
- 你也可以切到渲染视图
- 但系统不会强迫你只接受“总结后”的版本

### 画面三：团队开始围绕同一件事协作

以前是一条消息飞进群里，大家各自消化。

V3 之后，它应该开始像一个真正的事件：

- 有状态
- 有入口
- 有动作
- 有回看能力

也就是说，GoMessage 由此不再只是“通知”，而是开始承担“承接”的职责。

## 身份变化

V3 做完之后，GoMessage 的身份会发生一次很重要的变化：

- 以前它更像一个消息转发器
- 现在它开始像一个事件中枢

这层变化看起来并不张扬，但分量很重。

因为从这一步开始，GoMessage 才真正有资格承接后面的：

- 事件面板
- 交互卡片
- 团队协作
- AI 实习生
- Agent 生态

换句话说：

**V3 是 GoMessage 第一次真正形成产品层的版本。**

## 长期态度

V3 之所以重要，不只是因为它补上了若干能力，更因为它开始确立一种长期态度：

- 不急于显得聪明
- 不急于追逐热闹
- 先把事实接稳
- 先把秩序立住
- 先把用户真正依赖的部分做扎实

一个能够被长期使用的系统，未必一开始就最显眼；
但它通常会让人逐渐产生一种稳定的感受：

> 这个项目是认真做事的，而且愿意把事情持续做下去。

如果 V3 能把这种感受建立起来，它带来的就不只是功能提升，而是一种更可持续的信任基础。

## V3 的边界

### V3 要做什么

- 把 V2 的历史问题修干净
- 把消息升级成事件
- 把事件从“发完即结束”升级成“可打开、可查看、可处理、可追溯”
- 给未来 AI 时代提前准备秩序壳

### V3 不做什么

- 不做 AI 实习生
- 不做群聊里的智能人格
- 不默认替用户总结和判断
- 不把 GoMessage 做成另一个聊天软件

## V3 的核心画面

作者之前真正想要的，不只是“后台能力更完整”，而是用户未来会看到下面这些具体画面：

### 画面一：群里来了一条事件消息

它不是孤零零的一段文本。

它应该像一个有身份的事件卡片：

- 事件标题
- 事件级别
- 来源系统
- 关键字段
- 当前状态
- 一个“打开事件面板”的入口

### 画面二：点开之后，不是空白，而是事件面板

用户点开后，能看到：

- 原始 JSON
- 渲染后的消息
- 命中的模板
- 变量映射
- 推送到哪些客户端
- 推送是否成功
- 事件目前是什么状态

### 画面三：专业用户可以拒绝“多嘴”

对专业用户来说，最重要的不是“总结得很聪明”，而是：

- 原始事实可见
- 信息不要被过度加工
- 需要时再切换到更友好的视图

### 画面四：团队不只是收到消息，而是能围绕事件做动作

例如：

- 打开详情
- 认领
- 已读
- 忽略
- 关闭

这时 GoMessage 才不只是通知工具，而是开始承接团队协作。

## V3 的四大新增功能

这四块，才是 V3 最应该被明确写下来的新增能力。

### 一、事件收件箱 + 事件面板

这是 V3 最核心的一层。

目标：

- 不只是“发出去”
- 而是“能回来看”

建议能力：

- [ ] 事件收件箱 / 事件列表页
- [ ] 事件详情页
- [ ] 查看原始 JSON
- [ ] 查看渲染结果
- [ ] 查看变量映射
- [ ] 查看模板命中结果
- [ ] 查看推送客户端和推送结果
- [ ] 查看事件产生时间、接收时间、处理时间

为什么重要：

- 它让消息第一次拥有“背后的事件实体”
- 它让 GoMessage 从转发器变成事件入口
- 它是后续所有高级能力的起点

### 二、原始信息优先 + 多视图模式

这是作者尤其在意、也值得被认真对待的一层。

V3 不应该默认把所有信息都变成“总结腔”。

建议能力：

- [ ] 原始模式
- [ ] 渲染模式
- [ ] 轻解释模式
- [ ] 不同用户可选择默认视图
- [ ] 在事件页中一键切换原始 / 渲染
- [ ] 在分发时可配置“发原始信息”还是“发渲染信息”

为什么重要：

- 解决专业用户讨厌被“多嘴加工”的问题
- 让 GoMessage 保持克制
- 为未来 AI 能力设定边界：AI 是附加层，不是事实本体

### 三、消息卡片交互 + 事件状态流转

V3 应该开始让群消息不再只是静态文本。

建议能力：

- [ ] 消息中附带事件状态
- [ ] 支持从消息跳转到事件面板
- [ ] 支持认领
- [ ] 支持已读
- [ ] 支持忽略
- [ ] 支持关闭
- [ ] 记录状态变更时间
- [ ] 记录状态操作人

为什么重要：

- 这样 GoMessage 才真正开始进入团队处理流
- 这样未来才有“同意 / 拒绝 / 打开事件面板”这类交互的土壤
- 这也是 V4 AI 实习生后续参与工作的必要前提

### 四、订阅与分发机制

V3 不应该停留在“统一转发”。

它应该开始回答：

- 谁该收到
- 收到什么
- 用什么形式收到

建议能力：

- [ ] 按事件类型分发
- [ ] 按标签分发
- [ ] 按客户端分发
- [ ] 按角色 / 团队分发
- [ ] 支持原始信息订阅
- [ ] 支持渲染信息订阅
- [ ] 支持不同人收到不同层级的信息

为什么重要：

- 它让 GoMessage 从消息转发器走向消息分发系统
- 它是以后产品化的关键能力
- 它能真正解决不同角色对信息粒度的不同需求

## V3 的产品原则

### 1. 原始事实必须永远可达

- 原始 JSON 不能被藏起来
- 用户不能被迫只看加工后的结果
- 未来再强的 AI，也只能建立在原始事实之上

### 2. 先有秩序壳，后有 AI 灵魂

V3 的真正任务，是把秩序壳搭起来：

- 事件是什么
- 事件从哪来
- 事件发到哪去
- 事件处于什么状态
- 事件如何被打开和回看

没有这层壳，V4 的 AI 实习生就很容易退化成一个只会回复的附加功能。

### 3. 尊重专业用户

V3 必须明确偏向一种成熟产品气质：

- 不喧闹
- 不多嘴
- 不抢判断权
- 不强迫总结

### 4. 从“通知”走向“承重”

V3 要让 GoMessage 的价值，从“发出一条通知”升级为：

**承接一条事件。**

## V3 完成后的理想状态

如果 V3 做好了，GoMessage 应该呈现出下面这种样子：

- 群里有事件消息
- 点开能看到完整事件面板
- 专业用户能直接看原始信息
- 团队能围绕事件做处理动作
- 每条事件都能被追溯、被回看、被协作

这时 GoMessage 才真正完成一次身份升级：

**它不再只是把消息送出去，而是开始成为机器世界向人类汇报时的事件中枢。**
