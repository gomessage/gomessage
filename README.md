# GoMessage

> 让机器世界更清楚地向人类汇报。

GoMessage 是一个面向告警、Webhook 与任意 JSON 事件的消息转发系统。

它不替代监控系统，不替代聊天软件，也不试图抢走人类的判断。
它要做的，是补齐 `机器 -> 通知 -> 人类` 这条链路中最容易被重复开发、也最容易变得零散脆弱的那一段。

- 接收来自监控、Webhook、业务系统的结构化事件
- 将原始机器信息整理为适合人类阅读和处理的消息
- 将消息转发到钉钉、飞书、企业微信等客户端
- 用尽可能简单、稳定、可控的方式完成“机器向人类汇报”

GoMessage 从来不只是“发一条消息”这么简单。它真正想解决的是：**如何让机器世界更清楚、更稳定、更低成本地向人类汇报。**

它未必需要用喧闹的方式证明自己，但应该努力成为一种让人逐渐产生信任的基础能力：

- 说得清楚
- 站得住
- 用得久
- 在关键时刻靠得住

它更希望以一种克制、友好、可长期依赖的方式存在：

- 把事实接稳
- 把表达做好
- 把复杂留在系统内部
- 把判断尽量留给人

## 核心能力

- 一次接收，多端推送
- 支持 `Prometheus + Alertmanager` 告警消息接入
- 支持 Git `Webhook`、业务系统回调、任意 JSON 消息接入
- 支持多通道隔离，不同场景独立配置、独立入口、独立客户端
- 支持将聚合消息切分为单条逐一发送
- 支持原始数据劫持，便于观察上游 JSON 结构
- 支持通过模板将机器信息渲染成人类可读的信息体
- 模板支持 `if...else`、`for` 等逻辑编写
- 模板支持 `Markdown`
- 模板支持在文本中插入样式标签，控制展示效果

## 适用场景

- 监控告警通知
- Git / CI / 发布事件通知
- 各类业务系统 Webhook 转发
- 任意 JSON 结构转人类可读消息
- 内部自动化链路中的“机器向人汇报”环节

## 为什么会有 GoMessage

下面这段文字写于 GoMessage 早期阶段。这里尽量保留它本来的样子，因为直到今天，它仍然代表这个项目最核心的出发点。

> 过去几年有个问题让我思考了很久：随着内网基础设施自动化覆盖面越来越广，过去的`人类主动去盯梢关注`某些节点的工作方式，可能会无法满应对`未来海量的机器信息`扑面而来的局面；自动化越先进的场景下，越会逐渐演变成`人类没有多余精力`来持续跟进`自动化全链路`中多重节点了。那我们可否换一个方式来思考：是不是能让`机器自动来向人类汇报！`
>
> （请注意此处的侧重点）不再是机器把自身运行状况存储在某个中间的介质中`比如Promethus`，再借用Grafana用大盘展示出来；而是由机器或链路的某个节点，直接把自身某个运行状况主动的向人类推送汇报。人类只需要像读取微信消息一样，读取到机器发送的消息即可。
>
> 那么在整个 `机器--->通知--->人类` 的这个过程中，最被琐事淹没的环节就要数【`任意数据结构的json原始机器信息`都可以被转换成`人类可读的友好信息`的这个环节】最为占用我们的时间精力。具备开发力量的团队，可以使用Pyhon、Golang（或其它的某种开发语言）来编写一段程序，专门来干这个工作。但开发这个东西，开发者要分别阅读：钉钉客户端开发文档、微信客户端开发文档、飞书客户端开发文档、甚至短信发送开发文档、语音电话开发文档、等等。同时还要知道各种协议、标准、消息限流规范；甚至有的小伙伴还要关注程序运行的稳定性、高可用性，生产应急灾备恢复、等等的一堆问题。而缺乏开发力量的团队，则只能`通过增加人手去解决日益增长的需求`；面对这种客观存在的状况，在一定程度上浪费了团队的时间、精力、和珍贵的生产力。
>
> 作者认为这些`不同厂商的开发文档阅读`、`消息内容的渲染`、`零碎的代码调试`、`重复的思维复杂度投入`等等此类琐事都应该被消灭。同时`消灭琐事`刚好符合SRE技术哲学追求的一个重要方向，因此GoMessage在设计之初，就秉承着`更加简单高效的`帮助用户解放时间和精力为理念。不断地优化和打磨`消息渲染模块`，试图追求一种 `简单、再简单、更简单、简单到优美`的一种使用方式。（但由于作者的水平有限，对复杂问题的思考可能缺乏特有的视角，因此接下来的`消息渲染功能`在使用体验上可能依然存在某种复杂度，在此恳请各位小伙伴能够给于一些宝贵的反馈和建议，作者会在业余时间对GoMessage会不断的迭代更新下去，我们一起去做振奋人心的事~）

今天再回头看，这段初心最珍贵的地方，未必只是它提出了一个产品方向；
更在于它始终带着一种很克制、也很友好的愿望：

- 希望减少重复劳动
- 希望减轻人的消耗
- 希望让系统更清楚地向人类汇报
- 希望用不伤害人的方式，把复杂问题做得更简单

## 今天，GoMessage 仍然在解决同一个问题

今天的软件系统比几年前更复杂，自动化链路更长，消息来源更多，机器信息也更密集。

但 GoMessage 想解决的问题并没有变：

- 不让人类被原始机器信息淹没
- 不让团队重复编写零散、脆弱、不可复用的通知脚本
- 让机器世界能够以更清楚、更稳定、更可控的方式向人类汇报

GoMessage 会继续坚持这个初心：**尊重原始事实、提供清晰传达、减少重复劳动，并以一种克制、友好、可长期依赖的方式，把“机器向人类汇报”这件事持续做好。**

## 使用说明

### 多通道设计

`v3.x.x` 的一个核心能力是多通道并发工作。

每个通道都会自动生成一个独立消息入口，例如：

- `default` 通道：`http://<您的服务器地址>/go/message`
- `prometheus` 通道：`http://<您的服务器地址>/go/prometheus`

通道命名规则为：

```text
http://<您的服务器地址>/go/<您的通道名称>
```

例如：

```text
http://192.168.33.201:7077/go/message
http://192.168.33.201:7077/go/default
http://192.168.33.201:7077/go/prometheus
http://192.168.33.201:7077/go/zabbix
http://192.168.33.201:7077/go/dev
http://192.168.33.201:7077/go/fat
http://192.168.33.201:7077/go/prod
```

其中 `default` 通道有一个特殊别名：

- `路由 /go/message`
- `路由 /go/default`

二者在功能上等价。

这种设计是为了让用户在部署完成后，不增加记忆负担，直接就可以使用默认通道。如果您不需要这个通道，也可以随时删除。

### 创建新通道

可以通过界面中的【管理推送通道】对通道进行增、删、改、查。

需要注意的是：删除某个通道时，该通道下的所有资源也会一并删除，包括：

- 消息模板
- 接收客户端
- 用户变量映射

### 使用通道的正确姿势

一个通道由三个部分组成：

- 消息接收入口：接收上游 `POST` 推送
- 内容体渲染：将 JSON 渲染为人类可读的信息体
- 接收客户端：将渲染结果发送到指定客户端

### 消息接收入口

每个通道首页最重要的是两个内容：

- **消息推送地址**：直接复制给上游系统即可使用
- **模拟报警按钮**：用于快速验证当前通道是否畅通

模拟报警使用的是一段具有代表性的 JSON 数据，通常包含数组、字典和多层嵌套结构，可用于复杂推送场景测试。

### 接收客户端

通过【添加新客户端】可以创建对应的接收端。

客户端创建说明文档正在整理到 `docs/` 目录中，当前可以先参考界面中的表单说明与字段提示；如果现有客户端不能满足需求，也可以联系作者反馈具体使用场景。

### 数据渲染

GoMessage 尽可能采用一种简约、简单、兼容性较广的数据渲染方式，尽量摆脱过去那种只能在命令行里硬写配置文件、或者灵活度很低的通知模板方案。

你可以把它理解成：

- 上游负责产生结构化数据
- GoMessage 负责把机器信息变成人能看懂的话
- 下游客户端负责把消息准确送达

它的价值不在于替代监控、替代日志系统、替代聊天软件，而是在于补齐 `机器 -> 通知 -> 人类` 这条链路中最容易被重复开发、也最容易变得零散脆弱的那一段。

## 版本说明

假设当前版本为：`v3.0.0`

- `3` 代表大版本：底层架构发生了向前不兼容的更新或变动
- `0` 代表中版本：底层架构依然向前兼容，但增加了新的功能
- `0` 代表小版本：没有增加新功能，只对已知问题和缺陷进行了修复
